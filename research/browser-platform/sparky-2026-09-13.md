integrated Grace Blackwell CPU/GPU, 128 GB unified system memory, LPDDR5X,
and 10 Cortex-X925 + 10 Cortex-A725 cores. This corroborates, rather than
replaces, the observed Vulkan device type and shared heap topology.

**Established:** GB10 is reported as an integrated GPU and has unified-memory
architecture evidence. **Not established:** that this particular 140 W
GB10-based system is the owner-approved *representative modern integrated
graphics* target for §36. It must not be called a dedicated-GPU substitute
merely because the vendor is NVIDIA, nor automatically accepted because
Vulkan says integrated.

### Important sandbox distinction

`chrome://sandbox` reports:

```text
Layer 1 Sandbox: Namespace
PID namespaces: Yes
Network namespaces: Yes
Seccomp-BPF sandbox: Yes
Seccomp-BPF sandbox supports TSYNC: Yes
Ptrace Protection with Yama LSM (Broker): Yes
Ptrace Protection with Yama LSM (Non-broker): No
You are adequately sandboxed.
```

However, CDP separately reports **GPU `sandboxed: false`** for the working
Vulkan configuration. Browser/renderer namespace+seccomp checks are not a
GPU-process isolation certificate.

The final receipt corroborates this using only CDP-identified owned process
IDs: renderer processes have `NoNewPrivs: 1`, `Seccomp: 2` and one filter;
the GPU process has `NoNewPrivs: 1`, **`Seccomp: 0`, `Seccomp_filters: 0`**.
`NoNewPrivs` alone is not a seccomp sandbox.

A bounded per-launch trial of the supported `--gpu-sandbox-start-early`
option produced `webgpu: disabled_off`, `gpu_compositing: disabled_software`,
an empty GL renderer string, and no successful GPU sandbox attestation.
Renderer processes in that trial still reported `NoNewPrivs: 1`,
`Seccomp: 2`, `Seccomp_filters: 1`. That option was **not adopted**.
The trial processes/display were stopped. No security weakening was attempted.

The harness keeps sandboxing enabled, rejects disabling switches, records
this distinction and refuses **candidate benchmarks** when the GPU-process
sandbox is false/unknown. Current fixture/capture plumbing is usable;
a fully isolated candidate benchmark configuration is not verified here.

## Edge: official native Linux ARM64 option is absent

No installed `microsoft-edge`, `microsoft-edge-stable`, `microsoft-edge-beta`
or `microsoft-edge-dev` executable was found on PATH; `msedge` is also absent.
`dpkg-query` finds no `microsoft-edge*` package. The standard
`/opt/microsoft/msedge{,-beta,-dev}/msedge` executable locations do not exist.

The official [Edge enterprise release API][edge-api] was filtered to Linux
Stable/Beta/Dev releases. All currently offered Linux artifacts were **x64**:

| Channel | Latest observed Linux version | Architecture |
| --- | --- | --- |
| Stable | 153.0.4234.32 | x64 / Debian `amd64` |
| Beta | 154.0.4258.12 | x64 |
| Dev | 155.0.4268.0 | x64 |

The official [APT Release file][edge-release], dated
`Fri, 11 Sep 2026 21:30:23 +0000`, advertises `amd64 arm64 armhf all`.
**That generic repository architecture list is not evidence of an ARM64
Edge package.** The actual [ARM64 Packages.gz][edge-arm64] decompresses to
**zero bytes and zero packages**. The [AMD64 index][edge-amd64] contains 189
Stable versions and identifies:

```text
Package: microsoft-edge-stable
Version: 153.0.4234.32-1
Architecture: amd64
Filename: pool/main/m/microsoft-edge-stable/microsoft-edge-stable_153.0.4234.32-1_amd64.deb
SHA256: 1e7ed943dc84d22036f906691406d2530753df1b4923277234ea1006713b97d1
```

The official supported installation route is that vendor `.deb`/APT package
on a supported **x86-64 Linux** distribution. The metadata/download location
was investigated; the 64-bit Intel package was not installed, executed or
downloaded unnecessarily onto this ARM64 host. Extracting it with
`dpkg-deb -x` would still yield x86-64 executables; extraction is not an
ARM64 port or a supported sandbox setup. QEMU/Box64, Wine, a user-agent change,
Android Edge, and a renamed Chrome are not native desktop Edge proof.

[Microsoft's supported-OS document][edge-os] names supported 64-bit Linux
distributions and separately Windows and Apple Silicon. It does not turn
the empty Linux ARM64 package index into an installable artifact.

## Concrete remaining prerequisites

1. **Real Edge execution:** supply either an official usable Linux ARM64
   Edge release (none found) or an owner-provided existing environment
   supported by actual desktop Edge. A supported x86-64 Linux installation
   can use the official vendor packages; both real browsers must then be
   independently version-pinned and verified. No outside devices were
   scanned, no remote credentials requested and no paid infrastructure
   provisioned.
2. **Sandbox-compatible hardware WebGPU:** provide a browser/driver/profile
   where both renderer and GPU-process isolation are actually established,
   without disabling AppArmor, replacing the driver or bypassing profiles.
   The current working Sparky Vulkan profile cannot satisfy that gate.
3. **Representative target decision:** owner records the actual integrated
   GPU/browser/CPU/memory/OS/driver contract and its representativeness.
   GB10's classification is no longer speculative; qualification still is.
   These findings do not prescribe a speculative replacement GPU.
4. **Parent-owned acceptance inputs:** approved source pack, real renderer
   instrumentation and world/workload cases, source comparisons, audio,
   legitimate gameplay/persistence and explicit owner visual/audio approval.

The implementation and tests under `tools/browser-harness/` are complete as
capture/measurement infrastructure. The complete M1 platform/acceptance matrix
remains blocked by these concrete prerequisites.
